Assistente Motociclistico su Raspberry Pi

Valutazione di fattibilità, architettura e ruolo del modello linguistico in un sistema embedded safety-aware.

Documento di progetto · v0.1 · 2026-09-29

01 Il caso d'uso

Requisiti dichiarati

  • Warning e suggerimenti di guida in tempo reale
  • Manutenzione ordinaria e straordinaria (log + reminder)
  • Accesso a dati di bordo (strumentazione)
  • Posizione GPS e attività circostanti (POI)
  • Assistenza nella scelta dell'assicurazione
  • Raccomandazione prodotti e gite motociclistiche
  • Conoscenza del modello e del motore specifico
  • Hardware: Raspberry Pi connessa alla moto

È un sistema embedded con componenti eterogenei: sensori fisici, connettività esterna intermittente, un LM locale, e output multimodale (voce, display). Il modello linguistico è uno dei componenti, non il sistema nel suo insieme.

02 Vincolo hardware: Raspberry Pi

La scelta dell'hardware è il primo filtro tecnico. Raspberry Pi non ha GPU dedicata (salvo acceleratori esterni come Hailo AI HAT), quindi l'inferenza è CPU-only. llama.cpp supporta RPi nativamente via ARM NEON.

Hardware RAM max 45M Q8_0 (58 MB) 1.7B Q4 (~1 GB) 7B Q4 (~4 GB)
M2 Mac (Metal) 8 GB 418 t/s ✓ ~80 t/s ✓ ~30 t/s ✓
RPi 5 (ARM A76, 2.4 GHz) 8 GB ~25–35 t/s ✓ ~5–8 t/s ⚠ ~1–2 t/s ✗
RPi 4B (ARM A72, 1.5 GHz) 8 GB ~8–15 t/s ⚠ ~2–3 t/s ✗ <1 t/s ✗

Le stime di velocità per RPi sono inferite da benchmark pubblici llama.cpp su ARM; il modello SLM 45M non è stato misurato direttamente su RPi. La soglia minima per un assistente vocale fluido è circa 5–8 t/s (la sintesi vocale italiana media è ~12 parole/s, ~2 token/s utili): il SLM 45M Q8_0 supera questa soglia su entrambi i modelli di RPi.

Verdetto hardware Il modello SLM 45M Q8_0 (58 MB) gira in tempo reale su RPi 5 e con latenza accettabile su RPi 4. La RAM non è un vincolo. Modelli più grandi (1.7B+) diventano lenti su RPi 4 e richiedono RPi 5 con 8 GB.

03 Dominio safety-critical

La motociclistica è un dominio con componenti a rischio diretto: usura pastiglie freni, pressione pneumatici, viscosità olio motore, angolo di piega in curva. Un'informazione errata in questi ambiti può causare incidenti.

Rischio LM non supervisionato Un modello linguistico, incluso uno addestrato su Wikipedia italiana, genera testo plausibile ma non verificato. Non conosce le specifiche tecniche di un Kawasaki Z900 vs un Honda CB500F. Non distingue intervalli di manutenzione tra modelli diversi dello stesso produttore. Produrrà risposte confident e sbagliate con la stessa frequenza di risposte confident e corrette.

Il principio architetturale che ne deriva è non negoziabile:

In un sistema safety-aware, l'LM non può essere la fonte della verità. È il componente che formula la risposta, non quello che la conosce.

La conoscenza tecnica risiede in una knowledge base strutturata e verificata (manuali del costruttore, schede tecniche, database manutenzione). L'LM trasforma dati strutturati in linguaggio naturale italiano.

04 Architettura proposta

Il livello logico (rule-based) è il guardiano del sistema: conosce le soglie di allerta per ogni tipo di dato di bordo, interroga la knowledge base per la manutenzione, classifica l'intent dell'utente e passa all'LM solo la struttura della risposta da formulare. L'LM non vede mai dati grezzi; vede template da completare.

05 Cosa fa l'LM (e cosa non fa)

Può fare
  • Formattare dati strutturati in italiano naturale
  • Generare testo di allerta da template
  • Descrivere POI vicini da dati JSON
  • Rispondere a domande generali sulla cultura motociclistica
  • Riassumere log di manutenzione
  • Suggerire gite su tracce predefinite
Non può fare
  • Rispondere a domande tecniche senza KB
  • Conoscere intervalli specifici per modello
  • Diagnosticare errori OBD senza mapping
  • Dare consigli di guida safety-critical direttamente
  • Accedere al web in autonomia
  • Operare offline senza knowledge base
Esempio concreto Il livello logico legge l'OBD: olio a 4.200 km dall'ultimo cambio, soglia configurata a 5.000. Passa all'LM: {"alert": "maintenance", "item": "olio motore", "km_rimanenti": 800, "urgenza": "bassa"}. L'LM genera: "L'olio motore è al 84% della vita stimata. Hai ancora circa 800 km prima del prossimo cambio consigliato."

06 SFT: cosa addestrare

Per il ruolo di NLG layer, il SFT richiede esempi nella forma input strutturato → frase italiana. Nessun dialogo libero: l'input è sempre JSON deterministico, l'output è sempre una frase o un breve paragrafo. 

// Esempio SFT: allerta manutenzione
{
  "input": {"tipo": "manutenzione", "componente": "pastiglie_freno_ant",
            "usura_pct": 22, "km_totali": 18400, "urgenza": "alta"},
  "output": "Attenzione: le pastiglie del freno anteriore sono al 22% di vita residua.
             Con 18.400 km percorsi, è consigliabile sostituirle prima del prossimo viaggio."
}

// Esempio SFT: POI vicino
{
  "input": {"tipo": "poi", "categoria": "officina", "nome": "Moto Service Brescia",
            "distanza_km": 1.4, "aperto": true, "specializzazione": "Kawasaki"},
  "output": "A 1,4 km c'è Moto Service Brescia, specializzata in Kawasaki, aperta adesso."
}

// Esempio SFT: suggerimento gita
{
  "input": {"tipo": "gita", "percorso": "Lago di Como", "km": 85,
            "meteo": "soleggiato", "strade": "misto autostrada-statale"},
  "output": "Oggi si va bene per il giro del Lago di Como: 85 km, meteo soleggiato,
             misto autostrada e statale. Buon viaggio."
}

Con 500–1000 esempi di questo tipo, il SLM 45M impara il formato del dominio senza dover generalizzare su conoscenza tecnica. Il dataset è costruibile in pochi giorni a mano o con augmentation da un LLM più grande.

Fattibilità SFT Questo è il caso d'uso ideale per un SFT a basso volume su un modello piccolo: input deterministico, output breve, dominio ristretto, zero ambiguità semantica. 500 esempi sono sufficienti. Il rischio di hallucination è strutturalmente eliminato perché l'LM non genera mai contenuto fattuale, solo forma.

07 Alternative al SLM 45M

Se si vuole permettere all'utente query in linguaggio naturale più complesse (es. "spiega perché cambio l'olio ogni 5.000 km"), un modello più grande con instruction-following nativo è più adatto.

Modello Dim. Q4 RPi 5 (8GB) Instruction Italiano Nota
SLM 45M (nostro) 58 MB Q8 ~25 t/s Solo SFT Nativo NLG layer, nessuna Q&A
SmolLM2-360M ~230 MB ~15 t/s Base Limitato Opzione intermedia
Qwen2.5-0.5B-Instruct ~400 MB ~12 t/s Nativo Accettabile Buon compromesso
SmolLM2-1.7B-Instruct ~1.1 GB ~6 t/s Buono Limitato Solo RPi 5, 8GB
Phi-3.5-mini-Instruct ~2.2 GB ~2 t/s Ottimo Buono Troppo lento per RPi
Raccomandazione Per il prototipo: SLM 45M (nostro, controllato, veloce) + knowledge base strutturata per tutto ciò che è tecnico. Per Q&A più ricca in v2: Qwen2.5-0.5B-Instruct come drop-in replacement, stesso formato GGUF, compatibile con llama.cpp. Il cambio non richiede riscrivere l'architettura.

08 Matrice di decisione

Componente Tecnologia Decisione Motivazione
NLG (voce del sistema) SLM 45M Q8_0 + SFT GO Veloce su RPi, dominio ristretto, hallucination strutturalmente prevenuta
Regole di allerta Python rule-based GO Safety-critical: nessun LM su questa logica
Knowledge base manutenzione SQLite + schede costruttore GO Fonte di verità verificata, non generata
OBD / CAN bus python-obd o ELM327 GO Standard aperto, RPi compatibile via USB/Bluetooth
GPS + POI gpsd + Overpass API (OSM) DIPENDE Richiede connettività; offline richiede tile locali (>GB)
STT (input vocale) Whisper tiny/small DIPENDE Whisper tiny gira su RPi (~2-3 t/s); piccolo ritardo accettabile
TTS (output vocale) Piper TTS (italiano) GO Offline, RPi-native, voce italiana naturale, ~100 ms latenza
Q&A tecnica aperta LLM via API (cloud) DIPENDE Solo con connettività, non safety-critical, fallback a KB locale

09 Prossimi passi

Per il SLM (Run #5)

Run #5 può essere il SFT per il ruolo NLG nel sistema motociclistico: 500–1000 esempi nella forma JSON strutturato → frase italiana, copertura dei template principali (allerta, manutenzione, POI, meteo, gita). Il dataset è costruibile manualmente o con augmentation da GPT-4o/Claude.

Per il sistema completo

  1. Definire il sottoinsieme di dati OBD accessibili sul modello di moto target
  2. Costruire la knowledge base di manutenzione per quel modello (schema SQL)
  3. Prototipo rule-based → alert text senza LM (validazione logica)
  4. SFT sul SLM 45M con 200 esempi pilota, valutare qualità output
  5. Integrare Piper TTS italiano + STT Whisper tiny su RPi 5
  6. Decidere se servire Q&A tecnica da knowledge base locale o con fallback cloud
Valutazione complessiva Il caso d'uso è fattibile. L'architettura ibrida (regole + LM + KB) risolve il problema safety-critical separando la logica dalla voce. Il SLM 45M copre il ruolo NLG in modo efficiente su RPi. Il valore del progetto è nella qualità della knowledge base e nella robustezza del livello logico, non nella capacità del modello linguistico.
