SLM · Analisi di specializzazione · Case Study #2

Assistente per Gestione Email e Preventivi Assicurativi

Valutazione di fattibilità per un sistema di classificazione, estrazione campi e integrazione con sistema terzo su corpus mail e documenti assicurativi.

Documento di progetto · v0.1 · 2026-09-29

01 Il caso d'uso

Un broker o compagnia assicurativa riceve giornalmente decine o centinaia di email con richieste eterogenee: preventivi auto/moto/casa, rinnovi, segnalazioni sinistri, richieste di informazioni, reclami. L'operatore deve leggere, classificare, estrarre i campi rilevanti e inserirli nel gestionale. Il sistema proposto automatizza questa pipeline lasciando all'operatore solo i casi ambigui.

Differenza fondamentale rispetto al caso motociclistico Nel caso moto, l'LM formattava dati strutturati in linguaggio naturale. Qui fa il percorso inverso: riceve linguaggio naturale (email libere) e produce dati strutturati (JSON per il gestionale). È un compito di comprensione, non di generazione.

02 Vincoli normativi: GDPR e compliance assicurativa

Questo caso d'uso introduce il vincolo più critico dell'intera analisi: la gestione di dati personali sensibili in un contesto regolamentato.

GDPR — dati personali in training e inferenza Le email assicurative contengono PII (nome, CF, targa, indirizzo, storico sinistri). Usarle per il training richiede base giuridica (legittimo interesse o consenso esplicito), anonimizzazione o pseudonimizzazione prima dell'ingestion nel dataset, e un registro del trattamento. In produzione, i log di inferenza non devono conservare il testo delle email oltre il necessario.

La conseguenza pratica è che il sistema deve girare on-premise (nessuna email inviata a API cloud) e il modello deve essere addestrato su dati sintetici o anonimizzati. Questo è in realtà un argomento forte a favore di un piccolo modello locale rispetto a GPT-4 via API.

Compliance assicurativa (IVASS/CODASS) In Italia, la normativa assicurativa (CAP, disposizioni IVASS) impone requisiti specifici su tempi di risposta alle richieste e tracciabilità delle operazioni. Ogni azione automatica del sistema deve essere auditabile: chi ha inviato quale dato al gestionale, quando, con quale confidenza.

Nota architetturale: tool use senza agentic LM Il "tool use" non richiede che l'LM chiami strumenti in modo autonomo. L'LM estrae un JSON strutturato; Python legge quel JSON e chiama l'API. Questo è più affidabile di un modello agentico: ogni passo è deterministico e auditabile. L'LM fa solo la parte che sa fare: capire testo libero.

04 I due ruoli dell'LM

Classificazione ed estrazione sono compiti distinti. Possono usare lo stesso modello con prompt diversi (approccio semplice) o due modelli specializzati (approccio ottimale se la qualità lo richiede).

Classificazione

Input: testo email grezzo. Output: categoria + confidenza. È un task di classificazione multi-label: un'email può essere sia una richiesta preventivo sia una segnalazione sinistro. 

// Categorie principali (da definire con il dominio)
{
  "preventivo_auto":     true,
  "preventivo_moto":     false,
  "preventivo_casa":     false,
  "rinnovo_polizza":     false,
  "segnalazione_sinistro": false,
  "richiesta_info":      false,
  "reclamo":             false,
  "spam_irrilevante":    false,
  "confidenza":          0.91
}

Estrazione campi

Input: testo email + categoria classificata. Output: JSON con i campi rilevanti per quella categoria. I campi non trovati nel testo devono essere null, non inventati. 

// Estrazione per preventivo_auto
{
  "richiedente_nome":        "Marco Rossi",
  "richiedente_email":       "m.rossi@email.it",
  "veicolo_marca":           "Volkswagen",
  "veicolo_modello":         "Golf",
  "veicolo_anno":            2019,
  "veicolo_targa":           null,          // non presente in email
  "km_annui_stimati":        15000,
  "uso_veicolo":             "privato",
  "residenza_provincia":     "Milano",
  "copertura_richiesta":     "RC + furto",
  "sinistri_ultimi_5_anni":  0,
  "note_libere":             "cerca polizza con assistenza stradale"
}
Hallucination nei campi null Il rischio principale dell'estrazione è che il modello "inventi" campi non presenti nel testo per completare la struttura. Un campo null è corretto e gestibile; un campo con valore falso è un errore che entra nel gestionale. Il SFT deve includere molti esempi con campi null. La validazione rule-based deve cross-verificare i valori estraibili (formato targa AA000AA, CF 16 caratteri, date plausibili).

05 Il vincolo critico: lunghezza del contesto

Il SLM Run #4 ha max_seq_len = 512 token ≈ 380–420 parole. Questo è il principale vincolo tecnico per questo caso d'uso.

DocumentoLunghezza tipica (parole)Token stimatiCompatibilità 512
Email breve (richiesta info) 50–120 70–160 ✓ OK
Email media (preventivo) 120–300 160–400 ✓ OK
Email lunga (sinistro dettagliato) 300–600 400–800 ⚠ Troncamento
Clausola contrattuale singola 200–500 270–670 ⚠ Parziale
Contratto assicurativo completo 5.000–20.000 6.700–27.000 ✗ Impossibile
Regolamento IVASS (circolare) 2.000–10.000 2.700–13.000 ✗ Impossibile

Il SLM 512 copre bene le email (il target primario). Contratti e regolamenti richiedono chunking + RAG o un modello con contesto lungo. Per il prototipo, il corpus di training può essere limitato alle email; l'accesso a contratti/regolamenti può essere gestito da un retriever esterno che passa solo il chunk rilevante.

Opzione Run #5: aumentare max_seq_len a 1024 RoPE (già in uso nel Run #4) supporta teoricamente l'estensione del contesto senza re-training completo: i coefficienti di rotazione si ricalcolano per le nuove posizioni. In pratica, un fine-tuning su sequenze più lunghe migliora la qualità sull'estremità del contesto. Questo è una scelta da valutare prima di iniziare il SFT.

06 Dataset SFT: costruzione e volume

Il dataset deve coprire entrambi i compiti (classificazione + estrazione) con la distribuzione reale delle email del dominio. Deve essere costruito su dati sintetici o anonimizzati per ragioni GDPR.

Costruzione con LLM teacher (synthetic data)

Strategia raccomandata: usare GPT-4o o Claude come teacher per generare email sintetiche realistiche con le relative annotazioni corrette. Il teacher non vede email reali; genera variazioni plausibili da template di dominio forniti dall'operatore assicurativo. 

// Template per generazione sintetica

  "output_atteso": {
    "email": "Salve, vorrei un preventivo per la mia Fiat Panda del 2021...",
    "extraction": { "veicolo_marca": "Fiat", "veicolo_modello": "Panda", ... }
  }

07 Confronto con il caso motociclistico

Assistente Moto

  • LM: voce del sistema
  • Input: JSON strutturato da sensori
  • Output: testo italiano naturale
  • Constraint critico: safety fisica
  • Deployment: embedded (RPi)
  • Privacy: dati di bordo, basso rischio
  • SFT: JSON → frase (facile)
  • Ctx 512: sufficiente per l'output

Assistente Assicurativo

  • LM: elaboratore del testo
  • Input: email in linguaggio libero
  • Output: JSON strutturato
  • Constraint critico: GDPR + compliance
  • Deployment: on-premise server
  • Privacy: PII, alto rischio
  • SFT: email → JSON (medio)
  • Ctx 512: limite per email lunghe

Sono due direzioni opposte dello stesso paradigma: il moto usa l'LM come NLG (dati → linguaggio), l'assicurativo usa l'LM come NLU (linguaggio → dati). NLU è tecnicamente più difficile — la comprensione richiede più parametri e più esempi di training rispetto alla generazione su template.

08 Matrice di decisione

ComponenteTecnologiaDecisioneMotivazione
Classificazione email SLM 45M + SFT GO Task strutturato, output breve, alta fattibilità a 45M
Estrazione campi SLM 45M + SFT DIPENDE Funziona su email brevi/medie. Email >400 token richiedono ctx esteso o chunking
Validazione formato Rule-based Python GO Targa, CF, date: regex deterministici, non compito per l'LM
Tool call / API gestionale Python (non LM) GO L'LM produce JSON; Python chiama l'API. Più affidabile di un LM agentico.
Accesso contratti/regolamenti RAG + retriever DIPENDE Documenti troppo lunghi per ctx 512. Richiede chunking + embedding retrieval.
Human-in-the-loop Coda operatore OBBLIGATORIO Compliance IVASS + gestione casi ambigui. Non opzionale.
Audit log Structured logging GO Ogni estrazione e tool call deve essere tracciabile per compliance.
Training data Sintetico (LLM teacher) GO GDPR: non usare email reali per training senza anonimizzazione certificata

Raccomandazione finale Il caso assicurativo ha valore commerciale maggiore ma complessità e rischio compliance significativamente più alti. Il SLM 45M è borderline per l'estrazione da testi liberi: funziona sulle email brevi, ha difficoltà con quelle lunghe. La strategia ottimale è: SFT moto per Run #5 (architettura più semplice, rischio più basso, validazione rapida), poi affrontare il caso assicurativo con contesto esteso a 1024 token e pipeline RAG per i documenti lunghi.
