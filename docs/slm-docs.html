Introduzione

SLM (Small Language Model) è un modello linguistico decoder-only addestrato interamente da zero in Python con PyTorch. Il modello opera sulla lingua italiana, ed è progettato per essere comprensibile nei suoi meccanismi interni, ogni componente è scritto esplicitamente, senza librerie di alto livello che nascondano i dettagli.

L'architettura segue il paradigma GPT: un transformer autoregressivo che, dato un testo in ingresso, impara a prevedere il token successivo. Con sufficiente addestramento, questa capacità predittiva si traduce in generazione di testo coerente.

Il progetto è sia didattico che applicativo. La comprensione profonda dei meccanismi interni è parte esplicita degli obiettivi, non un effetto collaterale.

Meccanismo di Attenzione

L'attenzione è il meccanismo che permette al modello di considerare il contesto: ogni token può "guardare" tutti i token precedenti e pesarne la rilevanza per la propria rappresentazione.

Scaled Dot-Product Attention

Ogni token genera tre vettori: Query (cosa cerco?), Key (cosa offro?), Value (cosa comunico?). I pesi di attenzione si ottengono con:

$$\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

La divisione per $\sqrt{d_k}$ previene che il prodotto scalare cresca troppo al crescere della dimensione, rendendo il softmax instabile.

Causal Mask

Il modello è autoregressivo: la posizione $t$ non deve vedere le posizioni future $t+1, t+2, \ldots$ La maschera causale è una matrice triangolare inferiore che impone questo vincolo azzerando i pesi di attenzione verso il futuro:

# Matrice 4×4 per seq_len=4
  #   t=0: vede solo se stesso
  #   t=3: vede tutti i precedenti
[1, 0, 0, 0]
[1, 1, 0, 0]
[1, 1, 1, 0]
[1, 1, 1, 1]

Multi-Head Attention

Invece di un'unica attenzione su $d_{model}$ dimensioni, si usano 8 teste parallele ognuna su $d_k = d_{model}/8 = 32$ dimensioni. Ogni testa ha proiezioni $W_Q, W_K, W_V$ indipendenti e impara a "guardare" aspetti diversi delle relazioni tra token — sintattici, semantici, di co-riferimento, ecc.

$$\text{MultiHead}(Q,K,V) = \text{Concat}(\text{head}_1,\ldots,\text{head}_h)\,W^O$$

La specializzazione non è progettata esplicitamente: emerge durante il training per minimizzare la loss.

Blocco Transformer

Ogni blocco (TransformerBlock) combina attenzione e feed-forward con connessioni residue e normalizzazione. Si usa la variante pre-norm, più stabile del post-norm originale:

# Pre-norm: normalizza PRIMA di passare al sotto-strato
x = x + dropout( Attention( LayerNorm(x) ) )   # ← residual
x = x + dropout( FeedForward( LayerNorm(x) ) )  # ← residual

Positional Encoding

L'attenzione è invariante alla posizione: senza informazione posizionale il modello non distingue "gatto mangia topo" da "topo mangia gatto". Il positional encoding sinusoidale aggiunge al vettore di ogni token un segnale che codifica la sua posizione nella sequenza:

$$PE_{(pos,2i)} = \sin\!\left(\frac{pos}{10000^{2i/d_{model}}}\right), \quad PE_{(pos,2i+1)} = \cos\!\left(\frac{pos}{10000^{2i/d_{model}}}\right)$$

Frequenze diverse per dimensioni diverse — le basse frequenze codificano posizioni lontane, le alte posizioni vicine. Non è un parametro appreso: è fisso e aggiunto direttamente all'embedding.

Modello GPT

Embedding e Weight Tying

Ogni token viene convertito in un vettore denso da 512 dimensioni tramite una lookup table (nn.Embedding). La matrice di embedding (vocab_size × 512) è la stessa usata dall'ultimo layer lineare che proietta verso il vocabolario. Questa tecnica si chiama weight tying:

self.lm_head.weight = self.token_embedding.weight  # stesso tensore

Motivazione: il token "chiesa" come input e come output atteso condivide la stessa rappresentazione. Riduce il numero di parametri e migliora la generalizzazione. Vale per qualsiasi tokenizer — char-level o BPE.

Generazione autoregressiva

Il modello genera un token alla volta. Ad ogni step: (1) forward pass sull'intero contesto, (2) si considera solo il logit dell'ultimo token, (3) si applica temperatura e top-k, (4) si campiona la distribuzione risultante, (5) il nuovo token si aggiunge al contesto e si ripete.

ParametroEffettoValore consigliato
temperature= 1.0: distribuzione originale. < 1: più prevedibile. > 1: più creativo/casuale0.7 – 0.9
top_kCampiona solo tra i k token più probabili. Riduce le uscite incoerenti20 – 50

Fase 1 — Char-level (Run #1, completato)

Il tokenizer converte ogni carattere del testo in un intero, costruendo il vocabolario direttamente dal corpus. 102 caratteri unici sul corpus narrativo italiano (552 KB). Nessuna dipendenza esterna.

# Vocabolario costruito dal corpus
chars = sorted(set(open('corpus.txt').read()))  # 102 caratteri unici
stoi  = {c: i for i, c in enumerate(chars)}
itos  = {i: c for c, i in stoi.items()}

encode("gatto", stoi)    # → [1, 0, 3, 3, 2]
decode([1,0,3,3,2], itos)  # → "gatto"

Risultato: val loss 1.7256 in 46 minuti su MPS. Morfologia italiana corretta (suffissi -zione, -mente), nessuna coerenza semantica. Obiettivo centrato: validare che ogni componente funzionasse prima di scalare.

Fase 2 — BPE-SPM (Run #3 e successivi, completati)

BPE (Byte Pair Encoding) via SentencePiece. Vocabolario da 16 000 token addestrato sul corpus concatenato Wikipedia IT + narrativa. Il tokenizer è salvato nel checkpoint ed è autocontenuto: nessuna dipendenza esterna a runtime. Ogni checkpoint successivo (Run #4 con RoPE, SFT, LoRA adapter) riusa lo stesso vocabolario — il tokenizer è addestrato una volta sola e mai rigenerato.

# Training del tokenizer (una volta sola, già fatto in Run #3)
python3 train.py --tokenizer bpe-spm \
    --bpe-corpus data/corpus_bpe.txt --bpe-vocab 16000

# Uso successivo — riusa il modello SPM già nel checkpoint
python3 train.py --tokenizer bpe-spm --resume --data data/nuovi_shard.txt

# Inferenza con infer.py
python3 tools/infer.py --checkpoint checkpoints/best.pt "Descrivi Roma"

# SFT: stesso tokenizer, solo masked loss cambia
python3 train_sft.py --checkpoint checkpoints/best.pt --data data/sft_mini.jsonl

# LoRA: applica adapter al base model — tokenizer invariato
python3 train.py --lora --lora-rank 8 --checkpoint checkpoints/best.pt --data data/sft_mini.jsonl

Il BPE unisce iterativamente le coppie di token più frequenti. Sul corpus Wikipedia IT impara token come chiesa, comune, provincia, arcivescovo come unità atomiche — rilevanti per il registro enciclopedico. Loss iniziale attesa: log(16 000) ≈ 9.68.

Tokenizer nei run successivi

Il tokenizer non cambia dopo Run #3. Ogni run successivo (Run #4 con RoPE, SFT, LoRA) usa il modello SPM già salvato in best.pt. L'unico scenario in cui va rigenerato è se si vuole cambiare vocabolario o dominio linguistico in modo drastico — cosa che invaliderebbe tutti i checkpoint esistenti.

Dataset — Finestra Scorrevole

Il training usa la tecnica del Causal Language Modeling (CLM): il testo si etichetta da solo. Ogni finestra di seq_len+1 caratteri produce una coppia input/target in cui il target è l'input spostato di una posizione:

testo tokenizzato:  [g, a, t, t, o, ' ', m, a, n, g, i, ò, ...]

finestra i=0, seq_len=6:
  input  = [g, a, t, t, o, ' ']
  target = [a, t, t, o, ' ', m]

  ↳ il modello vede "g" e deve prevedere "a"
    vede "g,a" e deve prevedere "t"
    vede "g,a,t" e deve prevedere "t" ... ecc.

I batch sono campionati in posizioni casuali del corpus ad ogni step. Non si usa un DataLoader tradizionale: il campionamento casuale rompe già le correlazioni temporali.

Loop di Training

Ottimizzatore: AdamW

AdamW è la variante standard per i transformer. Combina Adam (learning rate adattivo per parametro, basato su media mobile di gradienti e gradienti²) con weight decay corretto (penalità $\lambda\|w\|^2$ che impedisce ai pesi di crescere senza controllo).

IperparametroValoreSignificato
lr3 × 10⁻⁴Learning rate massimo
min_lr3 × 10⁻⁵Learning rate minimo al termine del cosine decay
warmup_steps200Step di salita lineare 0 → lr (con pesi casuali, lr alto = passo errato enorme)
weight_decay0.1Forza della penalità L2 (solo su pesi ≥ 2D, non su bias/LayerNorm)
betas(0.9, 0.95)Decadimento memoria: gradienti e gradienti²
grad_clip1.0Gradient clipping: se ‖∇‖ > 1, scala il gradiente proporzionalmente

Learning Rate Schedule

Il learning rate segue una curva in due fasi. La curva sinusoidale (cosine decay) converge meglio di un taglio brusco perché riduce il passo progressivamente man mano che il modello si avvicina al minimo.

Gradient Clipping

Nei transformer profondi il gradiente può "esplodere" propagandosi attraverso molti layer — un singolo step aggiorna i pesi in modo devastante. Il clipping preserva la direzione del gradiente ma ne limita la magnitudine:

$$\nabla \leftarrow \nabla \cdot \min\!\left(1,\; \frac{\text{max\_norm}}{\|\nabla\|}\right)$$

Cosa Aspettarsi Durante il Training

Perplexity — quality scorer

La perplexity (PPL) misura quanto il modello è "sorpreso" da un testo: una sequenza simile alla distribuzione di training ha PPL bassa, una sequenza inattesa ha PPL alta.

Formula e scala

PPL = exp(loss) dove loss è la cross-entropy media token per token. Run #3 (addestrato su Wikipedia IT) ha val loss 4.08, quindi PPL ≈ 59 sul suo set di validazione.

Range PPLLivelloSignificato per Run #3
< 60BASSARegistro enciclopedico, italiano formale — come Wikipedia IT
60–150MEDIAItaliano buono, registro diverso da enciclopedico
150–400ALTATesto degradato o misto lingua
400+MOLTO ALTALingua straniera, spam, OCR difettoso

Cosa rileva (e cosa no)

La PPL non è un correttore grammaticale: misura la distanza dalla distribuzione di training. I risultati empirici su Run #3 mostrano un profilo preciso:

TipoRilevabileEsempio
Lingua stranieraSì — forte"hi O'sdg" → PPL 2240
Registro conversazionaleSì — forte"ciao sono francesco" → PPL 2690
Typo in entità nominateSì — forte"Saro Romano Impero" → PPL 615 vs "Sacro" → PPL 39
Errori morfosintattici comuniSegnale debole"ha fondando" → PPL 79 ≈ testo corretto
Errori semantici con entità corretteNoModello non ha world knowledge causale

Il meccanismo: entità nominate come "Sacro Romano Impero" compaiono migliaia di volte come unità coesa in Wikipedia — il modello conosce la sequenza con certezza quasi assoluta. Un typo che produce un token raro (Saro) rompe quella certezza. Un errore morfologico (ha fondando) usa token comuni in pattern simili presenti nel corpus — la sorpresa è contenuta.

Attenzione ai falsi negativi: testo ripetitivo (spam, boilerplate) è iper-prevedibile e ottiene PPL bassa. Il filtro PPL va sempre preceduto da un filtro euristico su linee duplicate e densità caratteri.

Uso come quality scorer

# REPL interattivo
python3 tools/eval_ppl.py

# Singolo testo

# Pipeline filtraggio corpus — scarta top 20% PPL
python3 tools/filter_corpus.py data/corpus_raw.txt \
    --checkpoint checkpoints/best.pt \

    --out data/corpus_clean.txt

# Con log dei documenti scartati (per ispezione manuale)
python3 tools/filter_corpus.py data/corpus_raw.txt \
    --checkpoint checkpoints/best.pt \
    --ppl-cut 0.95 --dedup \
    --out data/corpus_ppl95.txt \
    --rejected data/corpus_rejected.txt

Limite critico: il bias del quality scorer

Il PPL scorer è affidabile solo quando la distribuzione del scorer e quella del corpus target sono compatibili. Usare un modello addestrato su Wikipedia IT per filtrare testo web colloquiale introduce un bias sistematico: il modello giudica "sorprendente" l'italiano informale non perché sia di bassa qualità, ma perché non ne ha mai visto.

Esempio concreto: "ciao, sono Francesco" ottiene PPL 2690 su Run #4 (addestrato su Wikipedia). Non è testo degradato — è semplicemente un registro che il modello non ha mai incontrato. Applicare un cut percentile in questo contesto scarta preferenzialmente il testo colloquiale, rafforzando lo skew sintattico esistente invece di correggerlo.

Regola pratica:

  • Corpus enciclopedico / stesso dominio del training → PPL scorer affidabile
  • Corpus web / registro diverso dal training → solo filtro euristico + dedup; PPL scorer con soglia molto conservativa (p95+) per rimuovere solo garbage estremo
  • Dopo ogni run che amplia la distribuzione, il quality scorer va rivalutato sul nuovo modello
La scala di riferimento (BASSA/MEDIA/ALTA) è relativa al corpus di training del modello usato come scorer. Run #3/4 (Wikipedia IT) producono soglie valide per testo enciclopedico. Un modello addestrato su corpus più vari produrrà soglie diverse e più rappresentative dell'italiano moderno.

Corpus

La scelta del corpus è determinante per il carattere del modello. La legge di scaling di Chinchilla (Hoffmann et al. 2022) stabilisce che il punto ottimale di training è 20 token per parametro: per un modello da 45.9M parametri, il target è 918M token. Run #4 è stato addestrato su 47.8M token — il 5.3% dell'ottimale.

Qualità prima della quantità

Chinchilla dimostra che un modello più piccolo addestrato su più dati di qualità supera un modello più grande addestrato su meno dati. La conseguenza pratica: prima di scalare l'architettura, è necessario costruire un corpus adeguato. Questo ha guidato la ricerca delle fonti per Run #5.

Ricerca delle fonti — italiano moderno

Il vincolo principale: il pubblico dominio italiano copre per definizione autori morti da più di 70 anni — cioè italiano pre-novecentesco. I dataset PD (Liber Liber, PleIAs Italian-PD, Project Gutenberg) contengono italiano arcaico del XIII–XIX secolo, inappropriato per un modello su italiano contemporaneo.

I dataset web (Common Crawl, mC4, OSCAR) contengono italiano moderno ma non sono PD. Per uso di ricerca sono comunque utilizzabili — la licenza CommonCrawl permette l'uso non commerciale.

Hardware & Deploy

Il training è progettato per girare su qualsiasi hardware. Il checkpoint è autocontenuto e portabile: include pesi del modello, stato dell'ottimizzatore (tutti i momenti di Adam) e il tokenizer SPM — tutto il necessario per riprendere il training su un device diverso senza ricominciare da zero.

Device detection automatica

--device auto (default) seleziona automaticamente il migliore disponibile, con questa priorità:

# train.py — selezione device (train(), riga ~452)
if cfg.device == 'auto':
    if torch.backends.mps.is_available():   device = 'mps'   # Mac M1/M2/M3
    elif torch.cuda.is_available():         device = 'cuda'  # GPU Nvidia
    else:                                   device = 'cpu'   # fallback

Su Mac M2 seleziona MPS. Su EC2 con GPU Nvidia (MPS non disponibile) seleziona CUDA automaticamente. Il torch.load al resume usa map_location=device: i tensori vengono trasferiti sul device corretto indipendentemente da dove sono stati salvati. Override: --device cuda o --device mps.

Migrazione temporanea su hardware dedicato (EC2)

Processi paralleli e divergenza del checkpoint

Eseguire due istanze di train.py contemporaneamente a partire dallo stesso checkpoint non è training distribuito. È training parallelo non coordinato: i due processi divergono dal primo step.

Perché fg sul Mac non "salta" allo step dell'EC2

Un processo sospeso con Ctrl+Z (stato T — stopped) ha il suo intero stato in memoria RAM: pesi del modello, tutti i momenti di Adam per ogni parametro, step counter, seed del generatore casuale. Il file checkpoints/best.pt è uno snapshot scritto su disco a step 14 000 — il processo lo ha prodotto e poi ha continuato. fg risveglia il processo dalla RAM; non legge il file.

AzioneDa dove riparteLegge best.pt?
fg (processo sospeso)Stato in RAM — esattamente step 14 000 sul MacNo — stato in memoria
python3 train.py --resumeLegge best.pt dal disco, parte da step 14 000Sì — carica checkpoint

Meccanismo della divergenza stocastica

Se avvii sia il processo Mac (fg) che un processo EC2 (--resume), entrambi partono con gli stessi pesi a step 14 000. Ma get_batch() usa torch.randint senza seed fisso:

# TextDataset.get_batch() — campionamento casuale a ogni step
ix = torch.randint(n, (batch_size,))
# Mac:  [142, 8301, 27, ...]   — sequenza indipendente
# EC2:  [9443, 102, 5500, ...]  — sequenza diversa

Batch diversi → gradienti diversi → aggiornamenti diversi. I pesi divergono da step 14 001. Dopo 1 000 step i due modelli sono su traiettorie separate nello spazio dei parametri. Ognuno scrive il proprio best.pt in base alla propria val loss — sovrascrivendo il file dell'altro se condividono il filesystem, oppure producendo due checkpoint incomparabili su macchine separate.

StepProcesso A (Mac)Processo B (EC2)
14 000stessi pesi — da checkpoint
14 001batch [142, 8301, ...]batch [9443, 102, ...]
14 001∇A ≠ ∇B∇B ≠ ∇A
15 000pesi_A (traiettoria Mac)pesi_B ≠ pesi_A
30 000modello_Amodello_B — due modelli distinti

A 30 000 step avresti due modelli non confrontabili. Non esiste un'operazione "fondi i pesi" che preservi le proprietà di entrambi: la media dei pesi funziona solo in contesti specifici (ensemble o federated learning con garanzie formali di convergenza).

La differenza con PyTorch DDP (training distribuito): in DDP ogni processo calcola i gradienti su un shard diverso del batch, poi li aggrega con una all-reduce prima di aggiornare i pesi. Tutti i processi aggiornano gli stessi pesi, in sincrono, a ogni step. train.py non ha questa infrastruttura di comunicazione — è progettato per training sequenziale, mono-processo. La portabilità del checkpoint è orizzontale nel tempo (sospendi → riprendi), non spaziale (più macchine simultanee).

Controllo dell'inferenza: logit bias e token di fallback

Il vettore dei logit

Ad ogni passo di generazione il modello produce un vettore di 16.256 valori reali — uno per ogni token del vocabolario. Questi valori si chiamano logit: score grezzi, non normalizzati. Il softmax li trasforma in una distribuzione di probabilità; il campionatore (top-k, top-p, temperature) estrae il token successivo da quella distribuzione.

Logit bias

Il parametro logit_bias dell'endpoint /completion di llama-server accetta una lista di coppie [token_id, valore]. Immediatamente prima del softmax, il valore specificato viene sommato al logit del token corrispondente. L'operazione è:

logit_modificato[id] = logit_originale[id] + valore

Con valore = -100, il logit scende così in basso che dopo il softmax la probabilità del token è praticamente zero — non viene mai selezionato. Con valore = +10 si può invece favorire un token specifico.

Il logit bias agisce solo a inference time, senza modificare i pesi del modello. È reversibile: basta non passarlo nella richiesta successiva.

Token di fallback byte (indici 16000–16255)

Il vocabolario BPE-SPM addestrato sul corpus italiano contiene 16.000 token. La specifica GGUF richiede che il tokenizer sia in grado di codificare qualsiasi sequenza di byte, anche quelle non presenti nel vocabolario BPE. Per questo, durante la conversione, vengono aggiunti 256 token sintetici — uno per ogni byte possibile (0x00–0xFF) — agli indici 16000–16255. Ogni token corrisponde esattamente a un byte: <0x00>, <0x01>, …, <0xFF>.

Questi token di fallback sono token di emergenza: il tokenizer li usa solo per byte che non possono essere rappresentati altrimenti. In condizioni normali non dovrebbero mai comparire nell'output generato.

Perché i byte token diventano competitivi

Il corpus CulturaX contiene artefatti di encoding web: caratteri di controllo ASCII (tab, carriage return, form feed), byte non-printable da HTML mal decodificato, sequenze binarie in mezzo al testo. Il modello ha appreso che questi byte token compaiono in certi contesti — spesso dopo nomi propri rari, titoli di pagina, o intestazioni di sito.

Quando il modello incontra un contesto a alta incertezza (prompt insolito, nome proprio a bassa frequenza nel corpus), la distribuzione di probabilità si appiattisce: nessun token ha un vantaggio netto. In questo stato, i byte token — pur con probabilità individuale bassa — diventano competitivi rispetto ai token di testo. Con temperature=0.8 e top_p=0.9 il campionatore può selezionarli. Una volta generato un byte token, il contesto successivo spinge verso altri byte token: il loop si autoalimenta, l'output degenera in caratteri illeggibili.

Fix operativo

Generare l'array di bias per tutti i 256 byte token e passarlo ad ogni richiesta:

BIAS=$(python3 -c "import json; print(json.dumps([[i,-100] for i in range(16000,16256)]))")

curl http://localhost:8080/completion \
  -H "Content-Type: application/json" \
  -d "{
    \"prompt\": \"Il tuo prompt\",
    \"n_predict\": 150,
    \"temperature\": 0.8,
    \"top_p\": 0.9,
    \"repeat_penalty\": 1.3,
    \"logit_bias\": $BIAS
  }"

Con questo fix il vocabolario operativo scende a 16.000 token. Il modello non può più generare byte token, indipendentemente da quanto sia alta la loro probabilità nei pesi.

La presenza di byte token nell'output è anche un indicatore di qualità del corpus. La loro comparsa conferma che il corpus di training conteneva artefatti di encoding non filtrati. Il logit bias è una correzione a inference time, non una soluzione al problema corpus.

Corpus e conoscenza di dominio: analisi shard-by-shard

Un test sistematico su 8 prompt semantici (tecnico, estetico, letterario, storico, scientifico, procedurale) condotto su 6 modelli (run4-v6 + shard run6-aa/ab/ac/ad/ae) ha rivelato il cambio di distribuzione dovuto al passaggio da Wikipedia a CulturaX:
