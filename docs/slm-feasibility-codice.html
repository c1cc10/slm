01 La tesi: il vantaggio strutturale del modello piccolo

Questo è il caso d'uso in cui il modello piccolo non è un compromesso rispetto al modello grande: è la scelta corretta. Tre ragioni strutturali.

Corpus finito ed esauribile
Python ha decine di miliardi di righe su GitHub. Un linguaggio specializzato ne ha milioni — o meno. Un 45M può vedere l'intero corpus: non esiste "long tail" che sfugge al training.
Distribuzione concentrata
Il codice ha grammatica formale. A ogni posizione, i token validi sono un sottoinsieme piccolo. La distribuzione next-token è molto più concentrata che in prosa: il modello piccolo non deve distribuire capacità su variabilità infinita.
Contesto 512 token sufficiente
Una funzione media: 20-80 righe, 150-500 token. Il contesto locale è tutto ciò che serve per completamento. Nessun problema di lunghezza del contesto (al contrario della scrittura).
Output verificabile
Il codice generato può essere eseguito. Corretto o no è una risposta booleana. Non esiste questa proprietà per nessun altro caso d'uso nel set.
Copilot è mediocre per i linguaggi di nicchia perché il suo training corpus è dominato da Python, JS e Java. Un modello da 45M addestrato esclusivamente su ABAP, GDScript o un DSL interno ha visto tutto il codice che esiste in quel linguaggio, mentre Copilot ne ha visto una frazione rumorosa.

02 Differenza con il pre-training attuale

Il modello attuale è addestrato su Wikipedia IT: prosa enciclopedica, italiano, token di testo naturale. Il codice ha caratteristiche molto diverse.

CaratteristicaWikipedia IT (attuale)Codice sorgente
Vocabolario dominante parole italiane, punteggiatura keyword, identificatori, operatori, simboli
Struttura sintattica frasi, paragrafi, gerarchie di testo blocchi, indentazione, token terminali precisi
Sensibilità al whitespace nulla (spazi interscambiabili) critica in Python, significativa ovunque
Token boundaries BPE ottimizzate per morfologia IT subottimali per camelCase, ::, =>
Frequenza di sequenze ripetute bassa (variabilità narrativa) alta (boilerplate, pattern idiomatici)
Implicazione: ri-training o tokenizer specializzato Per un assistente al codice serio, il tokenizer BPE andrebbe ri-addestrato su un corpus misto codice + italiano (per i commenti). Un tokenizer ottimizzato per codice produce token più semanticamente densi: function → 1 token, non frammentato. Alternativa: usare un tokenizer esistente come cl100k_base (tiktoken) che già include vocabolario di codice. Il modello resterebbe 45M; cambierebbe la fase di tokenizzazione.

04 Candidati: quale linguaggio specializzato?

Il caso di massimo vantaggio: DSL proprietario Se un prodotto ha un suo linguaggio di configurazione, un suo query language, o un suo scripting engine — è impossibile che Copilot lo supporti. Un 45M addestrato sull'intero codebase interno diventa l'unico strumento che "capisce" quel linguaggio. La dimensione del corpus è gestibile (il codebase interno di un prodotto è nell'ordine di 1-50 MB di codice), e il modello può essere ri-addestrato a ogni rilascio.

05 Architettura: LSP server locale

Il deployment naturale per un assistente al codice è il protocollo LSP (Language Server Protocol), standard supportato da tutti gli editor moderni. Il SLM gira come processo locale; l'editor manda frammenti di codice, riceve completamenti. 

# Flusso completamento
Editor (VS Code / Neovim / JetBrains)
  │
  │  TCP socket (LSP)
  ▼
SLM Server (Python, FastAPI o asyncio raw)
  │
  │  context = prefix + suffix (fill-in-the-middle)
  │  max 512 token
  ▼
SLM 45M Q8_0 (llama.cpp, Metal/CUDA)
  │
  │  418 t/s → ~60ms per 25-token completion
  ▼
Response: { completions: ["..."] }
  │
  ▼
Editor inserisce il completamento

60 ms per un completamento di 25 token è più veloce di qualsiasi API remota (latenza di rete + processing). Il modello locale è sempre disponibile, funziona offline, non ha costi per token, non ha rate limit.

Fill-in-the-middle (FIM) Il completamento moderno non è solo "continua da qui" ma "riempi questo buco": data la porzione prima e dopo il cursore, genera il testo mancante. Richiede un formato di pre-training specifico: <PRE>...<SUF>...<MID>. Il modello impara questa struttura durante il training se il corpus è preparato con questo formato. Da valutare in fase di dataset preparation.

06 Dataset: pre-training su corpus + SFT opzionale

Track 1: pre-training diretto sul corpus codice

Per il completamento e il boilerplate, il pre-training auto-regressivo sul corpus codice è sufficiente. Non servono annotazioni: il modello impara i pattern dal codice stesso, esattamente come ha imparato l'italiano da Wikipedia.

Preparazione dataset codice
# Dataset preparation: corpus codice → training
# 1. Raccoglie tutti i file del linguaggio target
# 2. Filtra file troppo brevi (< 50 token) o troppo lunghi
# 3. Aggiunge separatori di file: <|file_start|> path/to/file.ext <|file_end|>
# 4. Opzionale: FIM shuffling (prepara il modello al fill-in-the-middle)
# 5. Finestre di 512 token con stride

import glob, os

def prepare_code_corpus(source_dirs, ext, out_path):
    docs = []
    for d in source_dirs:
        for f in glob.glob(f"{d}/**/*.{ext}", recursive=True):
            text = open(f).read()
            if len(text) > 200:                    # filtra file stub
                docs.append(f"# {f}\n{text}")
    with open(out_path, 'w') as fout:
        fout.write("\n\n".join(docs))

Track 2: SFT per instruction following (opzionale)

Se si vuole "scrivi una funzione che fa X" invece di solo autocompletamento, serve SFT su coppie (istruzione → codice). Volume: 300-600 esempi. Meno prioritario: il completamento locale copre il 90% dell'utilità.

08 Decisione: il caso tecnico più pulito

Il code assistant è il caso d'uso con la minor entropia di implementazione: nessun vincolo di compliance, nessuno stato persistente, nessuna infrastruttura complessa, contesto sufficiente, output verificabile, corpus finito. L'unica variabile aperta è la scelta del linguaggio target.

Raccomandazione Se esiste un linguaggio o DSL usato nei propri prodotti (Hokus, Tributum, Amel-IA, middleware) che non ha supporto AI adeguato, questo diventa il caso d'uso con il ROI più alto dell'intero set: il modello è l'unico strumento possibile per quel linguaggio, il corpus è controllato e aggiornabile, e il deployment come LSP server richiede meno di una settimana.
Training da zero o transfer? Due opzioni: (a) Pre-training da zero sul codice: richiede ri-addestramento completo con nuovo tokenizer. Risultato ottimale. Costo: un run completo. (b) SFT del modello IT esistente sul codice: riutilizza i pesi attuali, aggiunge la distribuzione del codice sopra. Tokenizer subottimale ma utilizzabile se il linguaggio target ha sintassi verbosa (SQL, HCL, ABAP). Per un DSL con molti simboli speciali (APL, regex avanzato) serve il pre-training.
