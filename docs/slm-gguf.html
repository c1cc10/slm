GGUF e Deploy con llama.cpp

Come un checkpoint PyTorch da 530 MB diventa un file standard che qualsiasi runtime compatibile può caricare — e cosa significa deployare un modello addestrato da zero fuori da Python.

Cos'è GGUF

GGUF (GGML Universal File) è il formato binario introdotto da llama.cpp nel 2023 per sostituire il precedente formato proprietario GGML. È diventato lo standard de facto per distribuire LLM quantizzati perché risolve tre problemi che i formati precedenti (PyTorch .pt, SafeTensors, HuggingFace bin) non affrontano:

  • Self-contained — tokenizer, metadati architetturali e pesi in un file solo
  • Quantizzazione nativa — supporta Q4_K_M, Q8_0 e altre 15+ varianti integrate
  • Memory-mapped — caricamento istantaneo senza deserializzazione, il kernel mappa il file in RAM

Un checkpoint PyTorch non è portabile: richiede Python, PyTorch, le stesse classi del modello definite nello stesso modulo. Un file GGUF è leggibile da qualsiasi runtime che supporti lo standard — llama.cpp, llama-server, llamafile, Ollama, LM Studio, Jan.

Versione usata in questo progetto llama.cpp build b11146 (versione 0.5.0), installato via Homebrew su macOS M2. La versione influenza la compatibilità — vedere la sezione "Note di compatibilità" a fine pagina.

Architettura nel GGUF: perché GPT-NeoX

GGUF non è un formato agnostico: ogni file dichiara un'architettura (general.architecture) e llama.cpp esegue il forward pass usando il codice specifico per quell'architettura. Scegliere quella sbagliata significa output privi di senso anche se i pesi sono corretti.

Il nostro modello ha tre proprietà architetturali che vincolano la scelta:

ProprietàNostro modelloArchitettura GGUF
Positional embeddingRoPE (Rotary)gptneox, llama, falcon
ActivationGELUgptneox (LLaMA usa SiLU)
Residual connectionsequenziale (pre-norm → attn → add, poi pre-norm → ffn → add)gptneox con use_parallel_residual=false

L'unica architettura che soddisfa tutte e tre è gptneox con use_parallel_residual = false. Questa flag distingue il comportamento sequenziale del nostro modello da quello parallelo di Pythia, che calcola attenzione e FFN contemporaneamente sulla stessa norma.

SALTATI — llama.cpp ricalcola RoPE internamente
QKV fusion llama.cpp si aspetta i pesi Q, K, V fusi in un singolo tensore per blocco di attenzione. Questo non altera i valori — è solo una concatenazione lungo la dimensione 0. La decomposizione avviene internamente durante il forward pass.

Il tokenizer e il problema di tokenizer.ggml.pre

Questa è la parte più sottile della conversione — e quella che ha causato l'errore unordered_map::at: key not found durante il test di inferenza.

La pipeline in due stadi

La tokenizzazione in llama.cpp non è un'operazione singola. Prima che qualsiasi ricerca nel vocabolario avvenga, il testo grezzo passa per una fase di pre-tokenizzazione:

Stadio 1 — Pre-tokenizzazione
"Il Parlamento europeo" →
▁Il ▁Parla mento ▁europeo

Il carattere ▁ (U+2581) è il marcatore di spazio di SentencePiece. Non è uno spazio ASCII — è un carattere Unicode distinto che fa parte del token.

↓
Stadio 2 — Lookup nel vocabolario
▁Il ▁Parla mento ▁europeo
→
4821 7203 1944 9118

Ogni chunk viene cercato nella mappa token_to_id. Se un chunk non esiste nella mappa, il codice C++ lancia std::out_of_range.

Il campo tokenizer.ggml.pre nel GGUF dichiara quale strategia usare allo stadio 1. Senza questa dichiarazione, llama.cpp v0.5.0 usa un default che potrebbe non corrispondere al comportamento del tokenizer usato durante il training.

Cosa è successo

Il nostro tokenizer è SentencePiece in modalità BPE, addestrato su Wikipedia italiana. LLaMA 1/2 usa lo stesso tipo di tokenizer e funziona correttamente con llama.cpp — ma dichiara esplicitamente il suo pre-tokenizer e ha un vocabolario più grande (32k) con byte fallback attivo: per ogni byte non rappresentato, esistono token speciali del tipo <0x41> che garantiscono la tokenizzabilità di qualsiasi stringa.

Il nostro vocabolario da 16k potrebbe non avere copertura completa per tutti i caratteri, oppure le opzioni di normalizzazione SPM usate durante il training (NFD, NFKC, lowercase) potrebbero differire da quelle che llama.cpp applica con il pre-tokenizer di default. Il risultato: alcuni chunk prodotti dallo stadio 1 non sono nella token_to_id map → crash.

Tokenizer funzionante — diagnosi corretta Il tokenizer è corretto. llama-tokenize conferma: "Il Parlamento europeo" → [181: ▁Il, 6362: ▁Parlamento, 4332: ▁europeo]. Il problema non era nel tokenizer ma nella chat interface di llama-cli, che cerca il newline token \n via unordered_map::at() senza try-catch. Il nostro vocabolario non ha un token \n esplicito → crash.

Diagnosi dettagliata

All'avvio, llama.cpp tenta di registrare il token del newline per usarlo nella formattazione della chat. Il codice GPT-NeoX in llama-vocab.cpp chiama token_to_id.at("\n"). La riga relativa a LLaMA/SPM è protetta da try-catch e produce solo un warning; il percorso di codice per gptneox potrebbe non avere la stessa protezione — da qui il crash non gestito in llama-cli.

La soluzione: llama-simple

llama-simple fa text completion pura senza chat interface, senza template e senza il lookup del newline token. Funziona correttamente. 

# Text completion con llama-simple (installato con llama.cpp)
llama-simple \
  -m slm-run4.gguf \
  -n 120 \
  --temp 0.85 \
  --top-k 40 \
  --top-p 0.9 \
  --repeat-penalty 1.3 \
  "Il Parlamento europeo"

Output su M2 (fp32, Metal): ~200–310 token/s. Caricamento modello ~670 ms.

La correzione permanente per llama-cli Aggiungere un token \n (newline) al vocabolario durante la conversione, oppure popolare il campo tokenizer.ggml.linefeed_id nel GGUF. Questo permetterà a llama-cli e llama-server di funzionare senza il workaround di llama-simple.

Sanity check del vocabolario

# Verifica copertura — da eseguire prima di ogni conversione
def check_coverage(sp, test_text="Il Parlamento europeo è fondato nel"):
    pieces = sp.encode_as_pieces(test_text)
    vocab_set = {sp.id_to_piece(i) for i in range(sp.vocab_size())}
    missing = [p for p in pieces if p not in vocab_set]
    if missing:
        print(f"ATTENZIONE: {len(missing)} pezzi non nel vocabolario: {missing}")
    return len(missing) == 0

Quantizzazione

Il file GGUF prodotto dal converter è fp32 (217 MB). La quantizzazione riduce la precisione numerica dei pesi per guadagnare in velocità e dimensione.

fp32
217 MB
Precisione piena, nessuna perdita. Base di partenza.
Q8_0
~55 MB
Int8 con scala fp32 per blocco. Qualità praticamente identica a fp32.
Q4_K_M
~35 MB
4 bit per peso, scala K-quant mixed. Ottimo rapporto qualità/dimensione.
Q2_K
~18 MB
2 bit per peso. Perdita misurabile su modelli piccoli — non consigliato sotto 1B.

Il comando di quantizzazione (quando il problema di compatibilità sarà risolto): 

# Produce slm-run4-q4_k_m.gguf (~35 MB)
llama-quantize slm-run4.gguf slm-run4-q4_k_m.gguf Q4_K_M

# Alternativa più conservativa
llama-quantize slm-run4.gguf slm-run4-q8_0.gguf Q8_0
llama-quantize e compatibilità architettura llama.cpp v0.5.0 ha rimosso gptneox dalla whitelist di llama-quantize. La quantizzazione richiede o una versione precedente di llama.cpp, o un quantizzatore Python alternativo (scrivibile con numpy, applicando Q8_0: scale = max(abs(row)) / 127, int8 = round(row / scale)).

llama-server: API OpenAI-compatibile

llama-server è incluso nella stessa installazione di llama.cpp e espone un endpoint HTTP compatibile con l'API OpenAI. Questo significa che qualsiasi client che usa OpenAI SDK può puntare al server locale senza modifiche. 

# Avvio del server (fp32, porta default 8080)
llama-server \
  --model slm-run4.gguf \
  --ctx-size 512 \
  --host 0.0.0.0 \
  --port 8080

# Con quantizzato (quando disponibile)
llama-server \
  --model slm-run4-q4_k_m.gguf \
  --ctx-size 512 \
  --n-gpu-layers 33     # offload su Metal (M2)

Endpoint esposti

POST
/v1/completions
Completamento testo — compatibile OpenAI legacy. Input: prompt, max_tokens, temperature, top_p.
POST
/v1/chat/completions
Chat in formato messages[]. Richiede chat template nel GGUF — non adatto senza SFT.
GET
/v1/models
Elenca il modello caricato con metadati (context length, architettura).
POST
/tokenize
Tokenizza una stringa e restituisce gli ID — utile per debug del tokenizer.

Uso da Python con OpenAI SDK

from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8080/v1",
    api_key="non-rilevante"  # llama-server non autentica in locale
)

response = client.completions.create(
    model="slm-run4",
    prompt="Il Parlamento europeo",
    max_tokens=80,
    temperature=0.8,
    top_p=0.9
)
print(response.choices[0].text)
Perché usare /completions e non /chat/completions Il nostro modello è un base model — un completatore di testo, non un assistente istruzionale. Il formato chat (system/user/assistant) richiede SFT su dati di conversazione. Fino a Run #5 (SFT), l'endpoint corretto è /v1/completions con un prompt grezzo.

llamafile: eseguibile autocontenuto

llamafile (Mozilla) è un singolo file eseguibile che contiene sia il modello GGUF che un runtime llama.cpp compilato per macOS/Linux/Windows. Non richiede installazione: si scarica, si rende eseguibile, si avvia. 

# Creazione llamafile da GGUF (richiede zipalign dalla toolchain llamafile)
cp /usr/local/bin/llamafile slm-run4.llamafile
zipalign -j0 slm-run4.llamafile slm-run4-q4_k_m.gguf
chmod +x slm-run4.llamafile

# Avvio — apre automaticamente un browser con interfaccia web
./slm-run4.llamafile

# In modalità server headless
./slm-run4.llamafile --server --nobrowser --port 8080

Il file risultante (slm-run4.llamafile) è distribuibile — chiunque può eseguirlo su qualsiasi macchina senza Python, PyTorch o llama.cpp installati. Per un modello da 35 MB (Q4_K_M), il llamafile pesa circa 38 MB.

Note di compatibilità (llama.cpp v0.5.0)

GPT-NeoX rimosso da llama-quantize Build b11146 non supporta la quantizzazione dell'architettura gptneox. La versione fp32 (217 MB) è scrivibile e caricabile, ma llama-quantize restituisce "unknown model architecture". Opzioni: downgrade a una build pre-b3000 via Homebrew, oppure implementare un quantizzatore Q8_0 in Python (circa 20 righe con numpy).
llama-cli crash — newline token non nel vocabolario La chat interface di llama-cli cerca \n via unordered_map::at("\n") senza try-catch nel percorso gptneox. Il nostro vocabolario BPE non ha un token newline esplicito → crash. Workaround: usare llama-simple per text completion pura. Fix permanente: aggiungere il token \n al vocabolario o settare tokenizer.ggml.linefeed_id nel GGUF.
Struttura GGUF verificata Il file è valido: architettura gptneox riconosciuta, 17 KV pair corretti, 147 tensori letti senza errori, use_parallel_residual = false presente, RoPE dimension count = 64 corretto.

Verso Run #5: GGUF e il task specifico

Il deploy via GGUF è la porta di uscita da Python verso il mondo reale. Ma l'utilità di un modello deployato dipende interamente da cosa sa fare.

Un base model come Run #4 esposto via /v1/completions è un completatore di testo — utile per scrittura assistita, generazione di bozze, completamento di pattern. Non è un assistente.

Il passaggio che trasforma il modello in qualcosa di utilizzabile in un contesto applicativo è il Supervised Fine-Tuning (SFT) su un task specifico. Con SFT, il modello impara a seguire istruzioni nella forma [contesto] → [azione richiesta] → [output strutturato], che è esattamente il pattern necessario per RAG, tool use e pipeline agentiche.

La scelta del task per Run #5 determina il valore del progetto — vedi Fine-tuning e Valutazione.
