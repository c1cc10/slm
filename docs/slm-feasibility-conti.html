Documento di progetto · v0.1 · 2026-09-29

01 Separazione netta: Python analizza, LM racconta

La gestione dei conti domestici è un caso con una divisione architettuale molto chiara. L'analisi finanziaria vera — aggregazioni, trend, forecast, anomalie — è matematica che Python esegue in modo deterministico. Il LM non fa analisi: genera la narrativa che rende quell'analisi comprensibile a un utente non tecnico.

Regola fondamentale Il LM non calcola mai. Riceve i risultati dei calcoli in JSON strutturato e li trasforma in italiano. Se il JSON dice "spesa ristoranti: +23% mese su mese", il LM genera "hai speso il 23% in più al ristorante rispetto al mese scorso". Non interpreta, non corregge, non arrotonda: traduce dati in prosa. La fonte di verità è sempre il dato numerico, non la frase generata.

03 I due ruoli del LM

Ruolo 1: categorizzatore di transazioni (NLU)

Le descrizioni delle transazioni bancarie sono testo breve e spesso criptico: "PAGO BANCOMAT CARREFOUR 14/09", "BONIFICO ENEL ENERGIA SP", "POS FARMACIA COMUNALE". Il LM mappa queste descrizioni su categorie di spesa.

Alta fattibilità: le descrizioni sono brevi (5–20 token), il numero di categorie è fisso, e la distribuzione è prevedibile (i commercianti dello stesso tipo hanno pattern lessicali simili). Il modello addestrato sui propri estratti conto impara le insegne commerciali specifiche del territorio.

Ruolo 2: narratore del report (NLG)

Riceve da Python un JSON con tutti gli aggregati e genera un report mensile leggibile, con i punti salienti evidenziati, le anomalie segnalate e i suggerimenti formulati come frasi naturali.

04 Analisi del conto corrente: caso pratico

Il caso concreto citato — analisi dei dati del conto corrente — si traduce direttamente in questa architettura:

  1. Export CSV dal home banking (Intesa/UniCredit/N26 lo offrono tutti): file con data, descrizione, importo, saldo
  2. Parser Python: normalizza il formato specifico della banca (ogni banca ha colonne diverse)
  3. LM categorizza ogni transazione dalla descrizione → categoria di spesa
  4. Python aggrega: totali per categoria, trend mese/mese, anomalie, forecast
  5. LM genera report mensile dal JSON aggregato, in italiano naturale
  6. LM risponde a domande: "quanto ho speso in farmacia quest'anno?" → Python calcola, LM risponde
Nota tecnica: formato CSV banche italiane Ogni banca italiana ha il proprio formato CSV (Intesa, UniCredit, Fineco, N26, Hype hanno tutti header diversi). Il parser Python deve essere calibrato per il formato specifico. Questo è lavoro di ingegneria, non di ML — ma va fatto prima del SFT. Alternativa: Open Banking API (PSD2) se la banca la supporta.

05 Privacy e sicurezza

Massima sensibilità finanziaria — on-device obbligatorio I dati bancari rivelano: pattern di consumo, reddito netto, abbonamenti attivi, medici frequentati (dalle farmacie), situazione debitoria, frequentazione di locali. Nessun dato deve uscire dal dispositivo. Nessuna API cloud, nessun modello remoto. Il database delle transazioni va cifrato a riposo (SQLCipher o simile).

08 Raccomandazione

Il caso conti domestici è architetturalmente pulito, ha un dataset costruibile senza dati reali sensibili, e produce un output di valore immediato per chiunque voglia avere una lettura chiara delle proprie finanze in italiano. Il rischio principale non è tecnico ma comportamentale: il report deve essere onesto e diretto (non rassicurante), e i suggerimenti non devono essere vaghissimi come quelli delle app bancarie mainstream.

Priorità: alta · Timeline: Run #6 Il prerequisito è il parser CSV per il formato della propria banca (1–2 giorni). Il SFT su dati sintetici è rapido (200–350 esempi, 2–3 giorni di costruzione). Il caso è naturalmente abbinato al caso analisi DB/log: stesso paradigma (Python analytics + LM narratore), stesso tipo di dataset. I due possono condividere il Track B del dataset SFT.
