SLM · Analisi di specializzazione · Case Study #7

Gestione Audio e Video

Valutazione di fattibilità per organizzazione di archivi multimediali, ricerca in linguaggio naturale su metadati, generazione di descrizioni e sottotitoli da trascrizioni.

Documento di progetto · v0.1 · 2026-09-29

01 Il vincolo principale: il LM non vede i file

Un SLM non può leggere un file audio o video. Non percepisce suoni né immagini. Tutto ciò che il LM può fare in questo caso d'uso dipende da metadati estratti da strumenti separati. Questa non è una limitazione di dimensione del modello — è strutturale per qualsiasi LM.

Il sistema si divide in due layer ben distinti: un layer di estrazione (non-LM) che processa i file e popola un database di metadati, e un layer LM che usa quei metadati come interfaccia in linguaggio naturale.

Il problema del cold start Se l'archivio esiste già (anni di foto e video non organizzati), il layer di estrazione deve essere eseguito una volta su tutti i file prima che il LM possa fare qualcosa. Per un archivio di 10.000 file, Whisper + EXIF + face recognition può richiedere ore. Il LM è pronto in minuti; l'infrastruttura richiede giorni di setup.

04 Ruolo del SLM: due task distinti

Task 1 — NL → query strutturata (NLU)

L'utente chiede in italiano; il LM traduce in criteri di ricerca per SQLite. Identico al caso assistente personale: alta fattibilità, contesto breve, output verificabile.

// NL → query
{
  "input": "tutte le registrazioni dove c'è Marco, estate 2021",
  "output": {
    "type": ["video", "audio"],
    "persons": ["Marco"],
    "date_from": "2021-06-01",
    "date_to": "2021-08-31"
  }
}

// NL → query per contenuto
{
  "input": "foto scattate in montagna",
  "output": {"type": "image", "tags": ["montagna"], "location_type": "mountain"}
}

Task 2 — metadati → testo italiano (NLG)

Dal record strutturato del database, il LM genera nomi file, didascalie, sinossi brevi. Stesso paradigma del caso moto: dati strutturati → testo. Alta fattibilità.

// Metadati → nome file
{
  "input": {"type":"video","date":"2022-06-15","persons":["Giulia"],"event":"laurea","location":"Milano"},
  "output": "2022-06-15_laurea_giulia_milano.mp4"
}

// Metadati → didascalia libreria
{
  "input": {"type":"album","event":"vacanza","location":"Sardegna","date":"2023-08","count":47,"persons":["famiglia"]},
  "output": "Vacanza in Sardegna, agosto 2023. 47 foto con tutta la famiglia."
}

// Transcript breve → sinossi
{
  "input": {"transcript": "Oggi parleremo del nuovo aggiornamento...", "duration_min": 12, "title": "Episodio 42"},
  "output": "Episodio 42: aggiornamenti sul progetto, roadmap per il secondo trimestre e discussione sulle nuove funzionalità annunciate la settimana scorsa."
}

06 Dataset SFT

Il SFT ha due track con dataset separati. Volume totale: 400–600 esempi.

  • Track NL → query (200–300 esempi): coppie (domanda NL, criteri JSON). Costruibile sinteticamente: genera domande da query SQL reali dell'archivio.
  • Track metadati → testo (200–300 esempi): record metadati → nome file / didascalia / sinossi. Costruibile sinteticamente: genera metadati casuali, scrivi manualmente le descrizioni target.

07 Raccomandazione

Il LM è pronto; l'infrastruttura è la sfida La parte LM (SFT, deployment) richiede 3–5 giorni. La pipeline upstream (Whisper + EXIF + face_recognition + YOLO su archivio esistente) richiede 1–3 settimane di setup e ore di processing per archivi grandi. Consiglio: avvia il SFT del LM subito; costruisci la pipeline in parallelo. Il valore più immediato è la ricerca NL + generazione nomi file, che richiede solo EXIF (rapido) e nessun modello ML aggiuntivo.
Connessione con la roadmap multimodale L'integrazione YOLO v3 già pianificata nella roadmap del progetto produce i tag visivi necessari per questo caso d'uso. I due track convergono: il modello YOLO genera tag → il LM li usa per ricerca e descrizione. Questo è il caso d'uso naturale per il milestone multimodale.
