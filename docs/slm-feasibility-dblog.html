Analisi DB e Log Applicativi

Valutazione di fattibilità per interfaccia in linguaggio naturale su database proprietari (text-to-SQL), classificazione di messaggi di log, generazione di alert narrativi e riassunti di pattern applicativi.

Documento di progetto · v0.1 · 2026-09-29

01 Due sotto-casi distinti

Questo case study comprende due domini tecnici accomunati dallo stesso paradigma architetturale: Python è l'analista, il LM è l'interfaccia. Le sfide specifiche sono però diverse.

DB dump — text-to-SQL
Domande in italiano → query SQL corrette per lo schema specifico → risultati → narrativa. Questo è il caso più interessante: elimina il bisogno di esposizione cloud per avere una query interface NL su dati privati.
Log applicativi — classificazione + alert
Messaggi di log → categoria/severity. Pattern anomali rilevati da Python → testo alert in italiano. Il LM classifica e descrive; non diagnostica le cause.

02 Text-to-SQL: il caso più strategico

Un'interfaccia in linguaggio naturale su un database proprietario è una delle funzionalità più richieste nel mondo enterprise — e una delle più difficili da ottenere senza esporre i dati a una API cloud. Il modello deve conoscere lo schema del database e saper tradurre domande informali in SQL corretto.

Vantaggio del modello piccolo specializzato Un modello grande generico (GPT-4, Claude) può fare text-to-SQL con lo schema nel prompt, ma richiede di mandare lo schema e la domanda a un'API esterna. Un 45M addestrato su quel solo schema conosce ogni tabella, ogni colonna, ogni relazione — e gira localmente, zero latenza di rete, zero dati esposti. Per database con dati sensibili (clienti, transazioni, pazienti), questa non è una preferenza: è un obbligo. 
// Esempi text-to-SQL per schema CRM semplice
{
  "schema_context": "Tabelle: users(id, name, email, created_at, plan), orders(id, user_id, amount, status, created_at), products(id, name, category, price)",
  "input": "quanti utenti si sono registrati questo mese?",
  "output": "SELECT COUNT(*) FROM users WHERE created_at >= date('now', 'start of month');"
}
{
  "input": "fatturato totale degli ordini completati negli ultimi 7 giorni per categoria prodotto",
  "output": "SELECT p.category, SUM(o.amount) as fatturato FROM orders o JOIN products p ON o.product_id = p.id WHERE o.status = 'completed' AND o.created_at >= date('now', '-7 days') GROUP BY p.category ORDER BY fatturato DESC;"
}
{
  "input": "quali utenti del piano pro non hanno fatto ordini negli ultimi 30 giorni?",
  "output": "SELECT u.name, u.email FROM users u WHERE u.plan = 'pro' AND u.id NOT IN (SELECT DISTINCT user_id FROM orders WHERE created_at >= date('now', '-30 days'));"
}

03 Vincolo di contesto: dimensione dello schema

Il modello deve "conoscere" lo schema per generare SQL corretto. Ci sono due strategie:

StrategiaCome funzionaLimiteQuando usare
Schema nel system promptCREATE TABLE inclusi nel context a runtimeOccupa token preziosi. ~3-5 tabelle medie entro 512 tokSchema piccolo, rapido da implementare
Schema nel SFTModello addestrato sullo schema specifico — lo conosce "a memoria"Nessun overhead runtime; usa 512 tok tutti per la domandaSchema stabile, dataset training costruito sullo schema
Schema lookup (RAG)Retrieval solo delle tabelle rilevanti per la domandaRichiede retriever aggiuntivoSchema grande (50+ tabelle)

Per un database proprietario con schema stabile (tipico di un prodotto software), il SFT con schema noto è la strategia ottimale. Il modello impara lo schema come parte del suo training — zero overhead a runtime.

04 Log applicativi: classificazione e alert

I log applicativi sono testo altamente strutturato e ripetitivo: timestamp, severity level, service name, message. Per un'applicazione specifica, i pattern di errore sono finiti e prevedibili — condizione ideale per un modello piccolo.

Cosa fa il LM
Classifica la severity (INFO/WARN/ERROR/CRITICAL), determina la categoria (network, database, auth, application), identifica il servizio coinvolto, genera testo di alert leggibile in italiano da un record di log.
Cosa fa Python
Conta le occorrenze, calcola le frequenze nel tempo, rileva anomalie statistiche (spike rispetto alla media), aggrega per finestre temporali, invia notifiche. L'analisi statistica è deterministica.
// Log record → classificazione + alert
{
  "input": {
    "timestamp": "2026-09-29T14:23:01",
    "level": "ERROR",
    "service": "api-gateway",
    "message": "Connection timeout to Redis at cache.internal:6379 after 5000ms",
    "occurrences_last_hour": 47,
    "baseline_hourly": 2
  },
  "output": {
    "category": "infrastructure",
    "subcategory": "cache",
    "severity": "high",
    "alert_text": "Attenzione: 47 timeout di connessione a Redis nell'ultima ora (baseline: ~2/h). Il servizio cache sembra non raggiungibile da api-gateway. Verificare la disponibilità di cache.internal:6379."
  }
}

05 Cosa il LM non deve fare

Diagnosi causa radice: fuori scope "Perché si verifica questo errore?" è una domanda a cui il LM non deve rispondere autonomamente. Le cause degli errori applicativi dipendono da configurazioni, versioni di software, stato del sistema, interazioni tra servizi — informazioni che il LM non ha e che non può ricavare dal solo messaggio di log. Una diagnosi confidente ma sbagliata può portare a interventi errati. Il LM descrive il pattern; il devops valuta la causa.

08 Connessione con i prodotti aziendali

Questo case study ha una connessione diretta con prodotti software che gestiscono database e log strutturati. Un SLM specializzato sul proprio schema potrebbe essere il componente di query interface, eliminando la necessità di esporre i dati degli utenti finali a un'API cloud solo per rispondere a domande interne sul proprio database.

Priorità: alta · Connessione diretta con prodotti aziendali Il text-to-SQL su schema proprietario risolve un problema concreto e immediato: dare al team la possibilità di interrogare il database in italiano senza scrivere SQL, senza esporre i dati a GPT-4, e senza aspettare che il team di BE implementi ogni query come endpoint. Schema piccolo + dataset costruibile in 2 giorni + SFT rapido.
