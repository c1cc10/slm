01 La differenza rispetto agli altri tre casi

I tre casi precedenti prevedono un LM che riceve input e produce output testuale. Questo caso è fondamentalmente diverso: l'assistente personale deve agire — chiamare API, leggere e scrivere stato persistente, generare notifiche autonome in assenza di input utente.

Non è un task di NLG (come moto) né di NLU (come assicurativo): è un task agentico. Il LM parse l'intent; un layer esterno esegue l'azione. La qualità del sistema dipende quasi più dalla robustezza del layer di orchestrazione che dalla qualità del LM.

03 Il ragionamento temporale

Tutti i task di questo assistente hanno una componente temporale. Questa è la sfida tecnica principale, non il linguaggio naturale in sé.

Le espressioni temporali in italiano formano uno spazio quasi illimitato: "venerdì prossimo", "prima di Natale", "tra una settimana o due", "il mercoledì di solito", "appena torno dalla palestra", "quando i bambini sono a scuola". Queste richiedono:

  1. Una data di riferimento (oggi) — sempre fornita dall'orchestrator, non dal LM
  2. Risoluzione di espressioni relative — regole deterministiche, non LM
  3. Interpretazione di espressioni vaghe — questa è la parte che il LM deve gestire
  4. Disambiguazione interattiva — "mercoledì prossimo fa comodo?" — il LM genera la domanda
Distribuzione del lavoro Il LM estrae l'espressione temporale raw: "martedì prossimo", "fine mese". L'orchestrator risolve in timestamp ISO. Se l'espressione è ambigua, l'orchestrator chiede al LM di generare una domanda di disambiguazione. Il LM non fa mai aritmetica su date — non è affidabile. Python sì.

04 Il vincolo privacy: il più severo di tutti

Questo è il caso d'uso con la maggiore densità di dati personali sensibili. Più dei dati assicurativi (GDPR ma business), più di qualsiasi altro:

Categoria datoEsempiClassificazione GDPR
Dati sanitari visite mediche, farmaci, ricoveri, patologie familiari Art. 9 — Categoria speciale
Dati di localizzazione calendario = dove sei e quando Sensibile per profilazione
Dati minori scadenze scolastiche, attività dei figli Art. 8 — Protezione rafforzata
Dati di routine lista spesa → pattern di consumo, abitudini, preferenze Profilazione comportamentale
Comunicazioni private email — contenuto potenzialmente riservato Riservatezza comunicazioni
Dati pet veterinario, farmaci animale Non regolamentato
Conseguenza obbligata: tutto on-device Nessun dato esce dal dispositivo. Nessuna API cloud, nessun modello remoto. Il SLM gira in locale. Il database è locale e cifrato. Questo non è una scelta di performance: è un requisito legale ed etico.

Su Raspberry Pi 5 (8GB) questo è realizzabile: il SLM 45M a Q8_0 occupa 58 MB. Il database SQLite per appuntamenti e liste di una famiglia occupa pochi MB. L'intero sistema può girare su hardware da 60 euro con consumi di 5 watt.

05 La questione dello stato: il LM non ricorda

Un LM, per definizione, non ha memoria tra sessioni. Ogni chiamata riceve un context window fresco. L'assistente personale ha state critico per definizione: la lista della spesa accumula voci, le scadenze persistono fino alla cancellazione, il calendario è permanente.

La soluzione è netta: il LM non è il database. Il LM è l'interfaccia. 

# Schema database locale (SQLite)
CREATE TABLE reminders (
    id          INTEGER PRIMARY KEY,
    category    TEXT,           -- 'medico' | 'spesa' | 'casa' | 'cane' | 'altro'
    subject     TEXT,
    person      TEXT,           -- NULL per sé stessi
    due_date    TEXT,           -- ISO 8601
    recurrence  TEXT,           -- NULL | 'weekly' | 'monthly' | 'yearly'
    done        INTEGER DEFAULT 0,
    created_at  TEXT
);

CREATE TABLE shopping_list (
    id       INTEGER PRIMARY KEY,
    item     TEXT,
    qty      TEXT,
    category TEXT,
    done     INTEGER DEFAULT 0
);

# Chiamata tipo: "cosa manca al frigorifero?"
# Orchestrator query: SELECT item FROM shopping_list WHERE done=0
# SLM genera risposta da lista: "Ti mancano: latte, uova, parmigiano"

06 Modalità proattiva: avvisi senza input

La funzionalità più utile non è rispondere a domande: è avvisare prima che l'utente debba chiedere. "Visita dal dentista dopodomani" senza che nessuno abbia fatto una query.

Trigger
Scheduler
Cron job ogni mattina alle 7:00
Query
Orchestrator
SELECT * FROM reminders WHERE due_date BETWEEN today AND today+2d AND done=0
Generazione
SLM 45M
Produce testo avviso naturale da record strutturato
Consegna
Notifier
Push locale, SMS, Telegram bot

Il SLM in questa fase fa un task di NLG puro — esattamente come il caso moto. Input: record strutturato. Output: testo italiano naturale per una notifica. Questo è il task per cui 45M è ottimale.

09 Decisione e raccomandazione

Il caso assistente personale è il più complesso dal punto di vista architetturale — non per il LM, ma per l'infrastruttura attorno al LM. Il SLM 45M fa la parte più semplice del sistema (parse NL → JSON, genera testo notifica); la parte difficile è il layer di orchestrazione, la gestione del database, l'integrazione con calendar e notification, il deployment sempre-acceso su RPi.

Cosa il SLM 45M fa bene in questo caso Intent classification su frasi brevi (80-150 char). Entity extraction: date, persone, oggetti. Generazione testo conferma e notifiche da template. Il contesto di 512 token è abbondante — le frasi di input sono molto più corte. Il modello non deve "capire" nulla di complesso: deve mappare pattern linguistici su strutture JSON. Questo è il task per cui i modelli piccoli sono stati usati con successo.
Blocco attuale: infrastruttura, non modello Il SFT del LM è la parte rapida (3-5 giorni). L'orchestrator Python con gestione database + calendar API + scheduler + sistema di notifiche è un progetto di 2-4 settimane separato. Prima di avviare il SFT, conviene decidere se si vuole investire nell'infrastruttura o se il SFT è solo per capire il pattern.

Come stepping stone: il SFT intent-extraction per questo caso è tecnicamente molto simile al SFT assicurativo (NL → JSON strutturato). I due dataset si possono costruire in parallelo e il training su uno beneficia l'altro. La differenza è solo il dominio dei JSON target.
